# AI 提示词六要素设计指南

本指南定义本仓库所有 AI 提示词、角色文档和方案文档的要素边界。任何提示词都由以下六个互不重叠的要素组成：

```text
Role + TechStack + Domain + Requirement + Constraints + Acceptance
```

六要素必须**分离存放**。把技术栈写进角色、把约束写进需求、把验收写进领域，都会让复用失效并放大提示词漂移。

## 六要素定义

| 要素 | 回答的问题 | 承载位置 | 生命周期 |
| --- | --- | --- | --- |
| `Role` | 我是谁，我的判断视角和职责边界是什么 | `Doc/AIPrompt/AIActor/<role>.md` | 长期稳定，跨任务复用 |
| `TechStack` | 用什么语言、框架、版本和工具 | 方案文档的「技术基线」章节 | 随项目演进 |
| `Domain` | 业务概念、术语、领域规则和数据含义 | 方案文档的「领域边界」章节、架构文档 | 随领域演进 |
| `Requirement` | 这次要做什么 | 方案文档的「目标」「需求范围」章节 | 单次任务 |
| `Constraints` | 不能做什么，必须怎么做 | 方案文档的「非目标」「执行约束」章节 | 单次任务 |
| `Acceptance` | 怎样算做完，怎样算做对 | 方案文档的「验收标准」「代码静态校验」「运行验证方式」章节 | 单次任务 |

## Role 的严格边界

`Role` **只**提供五项内容：

1. **身份**：这个角色是什么专业身份。
2. **核心职责**：在其专业范围内负责判断和产出什么。
3. **判断视角**：面对同一份代码或需求时，优先关注哪些维度、按什么顺序权衡。
4. **工作方式**：产出的组织方式、验证习惯、沟通粒度。
5. **职责边界**：明确不负责什么，遇到什么情况必须移交或停止。

`Role` 文档中**禁止**出现：

- 具体的库、框架、版本号、包名、命令行（属于 `TechStack`）。
- 具体的业务实体、状态机、业务规则（属于 `Domain`）。
- 本次任务要改哪些文件、实现哪些函数（属于 `Requirement`）。
- 目录白名单、禁止修改清单、安全红线（属于 `Constraints`）。
- 测试通过标准、性能指标、覆盖率门槛（属于 `Acceptance`）。

角色是**局部执行视角**，永远不能覆盖方案的范围、非目标、执行约束、安全规则或用户指令。当角色职责与执行约束冲突时，以执行约束为准。

## 方案文档中的角色使用

方案文档通过 `阶段角色与职责` 表把阶段映射到 Role：

| 列 | 含义 | 要求 |
| --- | --- | --- |
| 阶段 | 执行阶段名称 | 与「实现步骤」章节的阶段一一对应 |
| Role 索引 | 角色的精确索引名 | 必须与 `Doc/AIPrompt/AIActor/README.md` 的「角色文档」列完全一致 |
| 本阶段职责 | 该角色在本阶段的关注点 | 只能是角色文档职责的**子集或聚焦**，不得扩展 |
| 输出重点 | 本阶段应产出什么 | 属于 `Requirement`，不写进角色文档 |
| 切换条件 | 何时进入下一阶段 | 可判定，不使用「差不多」「基本完成」类表述 |

**索引规则**：必须使用精确索引（如 `architect`），不得使用显示名称（如「架构师」）、临时名称或泛化身份（如「开发」）。索引缺失、不存在、不一致或角色职责无法覆盖阶段职责时，执行方必须在修改任何文件前停止并询问用户。

## 一致性自检

编写或审查提示词、角色、方案时逐条确认：

- [ ] 每个要素只在一个位置定义，没有跨要素复制。
- [ ] Role 文档不含库名、版本、业务实体、文件路径和验收指标。
- [ ] 方案的每个必要阶段都有精确 Role 索引，且 `阶段角色与职责` 与 `实现步骤` 完全一致。
- [ ] 每个 Role 索引在角色目录中存在且对应文件可读。
- [ ] 阶段职责是角色职责的子集，没有借角色之名扩大权限。
- [ ] 约束与验收可判定，不依赖执行方主观解释。
