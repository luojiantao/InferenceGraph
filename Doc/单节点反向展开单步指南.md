# 单节点反向展开单步指南

本文说明 Agent 如何只对一个当前节点执行一次反向展开：找出它的直接前提节点集合，创建或复用这些前提节点，并建立从每个前提节点指向当前节点的候选推理边。

“反向”仅指规划时从当前结论回看它需要的前提。图中持久化的边始终按“前提 -> 当前节点”的方向保存。

## 核心流程：反向推理，正向验证

单节点反向展开的整体思路是**反向推理，正向验证**：

```text
获取当前节点的前提节点集合：反向推理
生成“前提节点 -> 当前节点”的候选推理边：发起正向验证
完成或阻断候选推理边：得到正向验证结果
```

生成推理边的目的就是正向验证。它把反向推理得到的前提假设转换成可领取、可取证、可完成或可阻断的验证任务。刚生成的边处于 `Candidate` 状态，表示正向验证已经发起，但尚未得到“成立”或“不成立”的结果；只有后续完成或阻断该边，才会产生验证结果。

因此，本指南定义的单步同时包含“获取前提集合”的反向推理和“生成候选推理边”的正向验证发起阶段，但不要求在同一步内完成取证并得出验证结果。

## 1. 单步范围

设当前节点为 `G`，本次规划得到一个直接前提集合：

```text
P = {P1, P2, ..., Pn}
```

一次单步反向展开只完成以下内容：

```text
读取 G 的上游依赖和下游语义上下文
  -> 规划 G 的直接前提集合 P
  -> 创建或复用 P 中的顶点
  -> 创建 P1 -> G、P2 -> G、...、Pn -> G 的候选推理边
```

本步骤在发起正向验证后结束，**不继续为 `P1`、`P2` 等前提寻找它们自己的上游前提**，也不领取、取证或完成刚创建的候选边。

当前节点 `G` 必须已经存在于会话中；它可以是 `Goal`、`State` 或 `Evidence` 顶点。通常反向展开的是 `Goal` 或尚待支持的 `State` 顶点。

## 2. 先确定直接前提集合

调用方 Agent 根据 `G` 的语义、领域规则和已有证据提出问题：

```text
要直接证明 G 成立，哪些条件、状态或证据需要成立？
这些条件是必须共同成立，还是各自都足以推出 G？
```

候选前提应是具体、可判断且可取证的命题，并且与 `G` 的对象范围和时间范围相匹配。只保留能直接支持 `G` 的前提：若 `P2` 只是 `P1` 的原因，则本次只建立 `P1 -> G`，不建立错误的 `P2 -> G` 捷径。

写入前先读取 `G` 的上游依赖上下文，避免重复或冲突建模：

```json
{
  "sessionId": "release-v1.2.0",
  "vertexId": "<currentVertexId>"
}
```

调用工具：`get_context_for_vertex`

再使用相同参数读取 `G` 的直接下游关系和到会话 Goal 的路径摘要：

```json
{
  "sessionId": "release-v1.2.0",
  "vertexId": "<currentVertexId>"
}
```

调用工具：`get_downstream_context_for_vertex`

`vertexId` 可以使用内部 ID，也可以使用会话内的 `Vn` 引用。响应中的 `context` 包含：

| 字段                        | 含义                                                            |
| --------------------------- | --------------------------------------------------------------- |
| `currentVertex`             | 本次准备反向展开的当前节点 `G`                                  |
| `goalVertex`                | 当前会话的 Goal 节点                                            |
| `directDownstreamEdges`     | 直接以 `G` 为前提的全部物理边，保留所有边状态                   |
| `directDownstreamVertices`  | 上述直接下游边指向的去重目标节点                                |
| `goalPathSummary.reachable` | 是否存在一条不经过 `Abandoned`、`Invalid` 边的已记录路径到 Goal |
| `goalPathSummary.hopCount`  | 最短路径的边数；不可达时为 `null`                               |
| `goalPathSummary.vertices`  | 按 `G -> ... -> Goal` 排列的路径节点                            |
| `goalPathSummary.edges`     | 按路径顺序排列的推理边                                          |

该接口不会返回完整下游子图，而是返回**全部直接下游关系和一条确定性的最短 Goal 路径**；相同长度的路径按稳定边 ID 顺序选择。若 `G` 就是 Goal，则 `reachable=true`、`hopCount=0`、`vertices=[G]`、`edges=[]`；若不可达，则 `reachable=false`、`hopCount=null`，路径节点和边均为空。

这些下游信息说明 `G` 正在被哪些已有公式消费，用于约束“为什么需要证明 `G`”以及新前提的语义是否符合下游目标，不得反过来作为证明 `G` 的证据。Goal 路径中的边仍可能是 `Candidate`、`Leased`、`Completed` 或 `Blocked`，因此路径存在不表示推导已经成立；路径中的一条物理边还可能属于 AND 公式，其他共同前提不会被伪造成这条线性路径的一部分，应通过 `formulaId` 判断完整公式。

这两个调用都只读取已有图，不会自动生成未知前提节点或推理边。

## 3. 创建或复用前提节点

对前提集合中的每个节点：

- 直接日志、文档、数据库记录或外部系统响应使用 `add_evidence_vertex`。
- 尚需进一步推导的中间条件使用 `add_state_vertex`。
- 已存在等价顶点时复用它，不要重复创建；可通过稳定的 `dedupeKey` 协助去重。

下面以两个中间状态前提为例：

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 1,
  "vertexId": "state.build-passed",
  "label": "版本 v1.2.0 构建通过",
  "payload": { "version": "v1.2.0" }
}
```

调用工具：`add_state_vertex`

每次成功写入后，保存响应中的 `vertex.vertexId` 和 `graphRevision`。下一次写请求的 `baseGraphRevision` 必须使用刚返回的最新版本。

## 4. 发起正向验证：创建前提指向当前节点的推理边

### 4.1 前提必须共同成立：AND

若所有前提都必须成立才能推出 `G`：

```text
P1 ∧ P2 ∧ ... ∧ Pn -> G
```

在**同一次** `propose_inference_edge` 调用中提交完整前提集合：

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 3,
  "sourceVertexIds": ["state.build-passed", "state.security-reviewed"],
  "targetVertexIds": ["<currentVertexId>"],
  "label": "构建和安全审计均通过，因此版本可以发布",
  "evidenceQuestions": [
    {
      "prompt": "构建和安全审计是否都满足版本发布条件？"
    }
  ]
}
```

调用工具：`propose_inference_edge`

服务会创建每个前提到当前节点的一条物理边：

```text
state.build-passed       -> G
state.security-reviewed  -> G
```

这些边共享同一个 `formulaId`，表达的仍是一个 AND 公式：

```text
state.build-passed ∧ state.security-reviewed -> G
```

不要把 AND 前提拆成多次单来源调用，否则会被建模为多个替代公式，而不是“所有前提必须同时成立”。

### 4.2 任一前提即可成立：OR

若 `P1`、`P2` 等是互相独立的替代解释：

```text
P1 -> G
P2 -> G
```

对每个前提分别调用一次 `propose_inference_edge`：

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 3,
  "sourceVertexIds": ["<premiseVertexId>"],
  "targetVertexIds": ["<currentVertexId>"],
  "label": "该前提直接支持当前节点"
}
```

每次调用都会创建一条从该前提到 `G` 的物理边，并分配不同的 `formulaId`，其语义为 OR。

## 5. 单步示例

当前节点：

```text
G：版本 v1.2.0 可以发布
```

本次只规划一层直接前提：

```text
P1：版本 v1.2.0 构建通过
P2：版本 v1.2.0 已通过安全审计

P1 ∧ P2 -> G
```

创建或复用 `P1`、`P2` 后，一次提交完整来源集合。结果图为：

```text
构建通过 --------> 版本可以发布
安全审计通过 ----> 版本可以发布
```

两条边共享公式组，因此只有两条边都完成且来源均得到支持时，`G` 才能被该公式正向支持。

本单步操作不会继续创建下列上游节点：

```text
CI 构建日志 -> 构建通过
安全审计报告 -> 安全审计通过
```

若需要这些关系，应在后续单独选择 `P1` 或 `P2` 作为新的当前节点，再执行一次相同的单步展开。

## 6. 伪代码

```text
expandBackwardOneStep(G):
  upstreamContext = get_context_for_vertex(G)
  downstreamContext = get_downstream_context_for_vertex(G)
  formulae = agentPlansDirectPremiseFormulae(G, upstreamContext, downstreamContext)

  for each formula in formulae:
    premises = createOrReuseVertices(formula.premises)
    propose_inference_edge(
      sources = premises,
      target = G,
      label = formula.label,
      evidenceQuestions = formula.evidenceQuestions
    )

  return createdOrReusedPremisesAndEdges
```

关键约束是：伪代码中没有 `expandBackwardOneStep(premise)`。前提节点只在本次创建或复用，不在本次继续展开。

## 7. 最小检查清单

- [ ] 已读取当前节点的上游依赖上下文。
- [ ] 已读取当前节点的直接下游关系和到 Goal 的路径摘要。
- [ ] 前提集合中的每个节点都是当前节点的直接前提。
- [ ] 每个前提节点均已创建或复用。
- [ ] 已创建从每个前提节点指向当前节点的候选推理边，发起正向验证。
- [ ] AND 前提在同一次 `propose_inference_edge` 调用中提交。
- [ ] OR 前提使用独立的 `propose_inference_edge` 调用提交。
- [ ] 每次写操作使用上一写操作返回的最新 `graphRevision`。
- [ ] 本次没有递归展开任何前提节点，也没有提前完成候选边。
