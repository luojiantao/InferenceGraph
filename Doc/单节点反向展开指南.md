# 单节点反向展开指南

本文说明 Agent 如何针对一个当前节点，以目标驱动的方式规划其前置条件，并将规划结果写入 InferenceGraph。

本文中的“反向”只指**规划和查找依赖时**从结论回看前提；持久化推理边仍始终按“前提 -> 结论”的正向方向保存和验证。

## 1. 先区分三件事

### 1.1 查询已知前置节点

若图中已经存在指向当前节点 `G` 的边，可使用：

- `get_vertex`：读取 `G` 的直接 `incomingEdgeIds`。
- `get_context_for_vertex`：读取 `G` 的上游依赖子图、已有证据摘要和全局概况。

这两个工具只读取已经记录在图中的内容，**不会自动生成未知前置节点**。

### 1.2 查询当前节点的下游语义约束

反向展开主要寻找 `G` 的上游前提，但当 `G` 是中间 `State` 时，还需要知道它正在支持什么结论、为什么需要继续证明它。调用：

```json
{
  "sessionId": "release-v1.2.0",
  "vertexId": "<currentVertexId>"
}
```

调用工具：`get_downstream_context_for_vertex`

`vertexId` 可以使用内部 ID 或会话内的 `Vn` 引用。响应中的关键字段为：

| 字段                        | 含义                                                            |
| --------------------------- | --------------------------------------------------------------- |
| `currentVertex`             | 当前节点 `G`                                                    |
| `goalVertex`                | 会话 Goal                                                       |
| `directDownstreamEdges`     | 直接以 `G` 为前提的全部物理边，保留所有状态                     |
| `directDownstreamVertices`  | 直接下游边指向的去重目标节点                                    |
| `goalPathSummary.reachable` | 是否存在一条不经过 `Abandoned`、`Invalid` 边的已记录路径到 Goal |
| `goalPathSummary.hopCount`  | 最短路径边数；不可达时为 `null`                                 |
| `goalPathSummary.vertices`  | 按 `G -> ... -> Goal` 排列的路径节点                            |
| `goalPathSummary.edges`     | 按路径顺序排列的推理边                                          |

该接口只返回全部直接下游关系和一条按边 ID 稳定选择的最短 Goal 路径，不返回完整下游子图。若 `G` 就是 Goal，路径为零跳；若 Goal 不可达，路径节点和边均为空。

下游路径只说明 `G` 在现有图中的用途，不能反过来证明 `G`。路径边可能仍处于 `Candidate`、`Leased` 或 `Blocked`，并且某条物理边可能只是 AND 公式中的一个前提，因此 `reachable=true` 不表示 Goal 已经得到支持。

### 1.3 发现未知前置节点

若当前节点没有足够的入边，调用方 Agent 需要根据节点语义、领域规则和已有证据提出规划问题：

```text
要证明当前节点成立，哪一组条件足够成立？
每个条件是直接证据、已知事实，还是还需要继续推导的状态？
这些条件是必须同时满足，还是存在可选的替代路径？
```

这一步是 Agent 的规划工作，不是 InferenceGraph 内置的自动推理工具调用。

## 2. 单节点展开算法

设当前节点为 `G`。

1. 调用 `get_context_for_vertex(sessionId, G)`，读取已有上游依赖，避免重复或矛盾建模。
2. 调用 `get_downstream_context_for_vertex(sessionId, G)`，读取直接下游关系和到 Goal 的路径摘要，确认 `G` 的用途和语义约束。
3. 综合上下游上下文，针对 `G` 生成一个或多个候选前提集合；不得把下游结论当作证明 `G` 的证据。
4. 将每个前提分类为：
   - `Evidence`：日志、文档、数据库记录、外部系统响应等直接证据。
   - `State`：需要由其他条件推出的中间状态，或被明确作为已知事实的状态。
5. 使用 `add_evidence_vertex` 或 `add_state_vertex` 创建尚不存在的前置节点。
6. 对每个候选前提集合调用一次 `propose_inference_edge`，方向固定为“前提集合 -> G”。
7. 对其中尚未落到直接证据、且尚未有完整支持路径的 `State` 节点递归执行步骤 1-6。
8. 当分支都落到可信基础证据后，从底层边开始取证、完成边，最后由正向支持计算确认 `G`。

伪代码如下：

```text
expand(G):
  upstreamContext = get_context_for_vertex(G)
  downstreamContext = get_downstream_context_for_vertex(G)
  knownFormulae = read existing incoming formulae from upstreamContext

  candidateFormulae = agentPlans(G, upstreamContext, downstreamContext)
  for each formula in candidateFormulae:
    premises = createMissingStateOrEvidenceVertices(formula.premises)
    propose_inference_edge(sources = premises, target = G)

  for each premise in candidateFormulae that is an unresolved State:
    expand(premise)
```

## 3. 示例：从“允许发布”反向展开

当前节点：

```text
G：版本 v1.2.0 可以发布
```

### 3.1 读取当前节点

```json
{
  "sessionId": "release-v1.2.0",
  "vertexId": "<goalVertexId>"
}
```

先调用 `get_context_for_vertex`。对新建 Goal 而言，返回的 `ancestorVertices` 和 `ancestorEdges` 通常为空。这表示当前图中还没有已知前提，并不表示目标已经成立。

再以相同参数调用 `get_downstream_context_for_vertex`。因为当前节点本身就是 Goal，典型返回为：

```json
{
  "directDownstreamEdges": [],
  "directDownstreamVertices": [],
  "goalPathSummary": {
    "reachable": true,
    "hopCount": 0,
    "vertices": ["<goalVertex>"],
    "edges": []
  }
}
```

上例只简写节点对象为占位文本；真实响应中的 `vertices` 是完整顶点对象。零跳路径表示“当前节点就是 Goal”，不表示 Goal 已经成立。

### 3.2 Agent 提出前提集合

Agent 根据发布规则提出：

```text
F1：构建通过 ∧ 安全审计通过 -> 版本可以发布
```

这里得到两个前置节点：

```text
P1：构建通过
P2：安全审计通过
```

它们都不是直接证据，先创建为 `State`：

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 1,
  "vertexId": "state.build-passed",
  "label": "版本 v1.2.0 构建通过",
  "payload": { "version": "v1.2.0" }
}
```

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 2,
  "vertexId": "state.security-reviewed",
  "label": "版本 v1.2.0 已通过安全审计",
  "payload": { "version": "v1.2.0" }
}
```

示例假设创建会话后的版本为 `1`，且没有并发写入。`baseGraphRevision` 必须是整数；每次写入后，都必须将下一次请求中的该值更新为刚返回的 `graphRevision`。

### 3.3 一次调用建立 AND 公式

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 3,
  "sourceVertexIds": ["state.build-passed", "state.security-reviewed"],
  "targetVertexIds": ["<goalVertexId>"],
  "label": "构建和安全审计均通过，因此版本可以发布",
  "evidenceQuestions": [
    {
      "prompt": "构建是否以退出码 0 完成，且不存在编译错误？"
    },
    {
      "prompt": "安全审计是否不存在阻断发布的高危问题？"
    }
  ]
}
```

服务会创建两条独立边，但它们具有同一个 `formulaId`：

```text
state.build-passed       -> G  (E1)
state.security-reviewed  -> G  (E2)

公式 F1：E1 ∧ E2，即 P1 ∧ P2 -> G
```

不需要、也不存在额外的“创建推理公式”调用；公式组在 `propose_inference_edge` 时自动建立。

`evidenceQuestions` 会复制到该批次创建的每条物理边。上例中的两个问题因此会同时附着在 `E1` 和 `E2` 上；若不同前提需要不同的问题，应在创建公式组后，对各条仍处于 `Candidate` 状态的边分别调用 `update_inference_edge` 设置其完整问题列表。

### 3.4 递归展开中间状态

`P1` 仍未被直接证据支持，继续将它作为当前节点：

```text
当前节点 P1：版本 v1.2.0 构建通过

反向规划：什么能够证明 P1？
E1：本次 CI 构建日志
E2：构建产物校验记录

E1 ∧ E2 -> P1
```

此时调用 `get_downstream_context_for_vertex(P1)`，可以看到 `P1 -> G` 的直接下游边，以及 `P1 -> G` 的 Goal 路径摘要。这些信息确认本次展开的 `P1` 正用于支持“版本可以发布”，但不能作为 `P1` 已成立的证据。

创建两个 `Evidence` 节点后，调用：

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 6,
  "sourceVertexIds": ["evidence.ci-build-log", "evidence.build-artifact-check"],
  "targetVertexIds": ["state.build-passed"],
  "label": "CI 构建日志和产物校验记录支持构建通过"
}
```

对 `P2` 采用相同方法，直到每个分支落到真实 `Evidence` 顶点或被明确认可的基础 `State` 顶点。

最终图的方向是：

```text
CI 构建日志 + 产物校验 -> 构建通过 ─┐
                                      ├-> 版本可以发布
安全审计报告 -----------> 安全审计通过 ─┘
```

规划时从右向左思考；边保存、完成和目标验证时从左向右进行。

## 4. AND 与 OR 的正确建模

### AND：所有前置条件都必须成立

```text
P1 ∧ P2 -> G
```

对同一目标使用一次多来源调用：

```json
{
  "sourceVertexIds": ["P1", "P2"],
  "targetVertexIds": ["G"],
  "label": "P1 和 P2 共同支持 G"
}
```

同一次调用中的来源共享一个公式组。组内每条边都完成后，公式才可支持 `G`。

### OR：任一条替代路径成立即可

```text
P1 -> G
P2 -> G
```

使用两次独立调用：

```json
{
  "sourceVertexIds": ["P1"],
  "targetVertexIds": ["G"],
  "label": "P1 支持 G"
}
```

```json
{
  "sourceVertexIds": ["P2"],
  "targetVertexIds": ["G"],
  "label": "P2 支持 G"
}
```

两次调用产生两个不同的公式组；任一完整组都可支持 `G`。

> 不要将 AND 前提拆成多次单来源调用。那会被建模为 OR，而不是“所有前提均成立”。

## 5. 假设、问题与证据的边界

| 项目     | 作用                             | 在图中的表达                                    |
| -------- | -------------------------------- | ----------------------------------------------- |
| 规划问题 | 帮助 Agent 发现需要证明的条件    | Agent 的分析过程，不是单独的 MCP 实体           |
| 候选前提 | 尚待证明的中间条件               | `State` 顶点，并继续为其建立入边公式            |
| 证据问题 | 验证某一候选推理关系             | `propose_inference_edge` 的 `evidenceQuestions` |
| 直接证据 | 日志、文档、外部记录等可追溯材料 | `Evidence` 顶点                                 |

当前实现没有独立的 `Hypothesis` 顶点类型。不要把尚未验证的假设作为孤立 `State` 节点长期使用：没有入边公式的 `State` 会被视为基础条件。对于待推导的状态，应尽快建立其上游候选公式，直到它可由证据或明确给定事实支持。

## 6. 从规划切换到执行

反向展开完成后，按依赖的底层到上层处理：

1. 用 `list_candidate_edges` 找到候选边。
2. 用 `claim_inference_edge` 获取边的租约、上下文和 `contextHash`。
3. 用 `answer_evidence_question` 记录每个问题的回答。
4. 用 `complete_inference_edge` 完成该边；无法成立时用 `block_inference_edge`。
5. 重复处理上层边，直至目标被已完成公式正向支持。

InferenceGraph 不会自行生成前提、回答问题或编造结论；它负责持久化上述规划结果、调度候选边并校验图结构和完成状态。

## 7. 最小检查清单

- [ ] 已读取当前节点的上游依赖上下文，未重复创建同一依赖。
- [ ] 已读取当前节点的直接下游关系和到 Goal 的路径摘要。
- [ ] 只把下游信息作为语义约束，未将下游结论反过来作为当前节点的证据。
- [ ] 每个候选前提集合的逻辑关系已经判定为 AND 或 OR。
- [ ] AND 前提在同一次 `propose_inference_edge` 调用中提交。
- [ ] OR 替代路径使用独立的 `propose_inference_edge` 调用提交。
- [ ] 每个未证实的中间 `State` 都有继续向上游展开的计划。
- [ ] 叶子节点是可追溯的 `Evidence` 或明确认可的基础状态。
- [ ] 所有写请求使用上一写请求返回的最新 `graphRevision`。
