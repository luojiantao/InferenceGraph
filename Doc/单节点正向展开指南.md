# 单节点正向展开指南

本文说明 Agent 如何从一个已知节点出发，规划它能够支持的后继结论，并将结果写入 InferenceGraph。

正向展开与[单节点反向展开指南](单节点反向展开指南.md)互补：反向展开从结论寻找前提；正向展开从前提寻找可能的结论。无论采用哪种规划视角，持久化推理边都固定为“前提 -> 结论”。

> 当前 InferenceGraph 不会根据节点文本自动发现后继结论，也不会调用 LLM 或外部规则库。发现新结论是调用方 Agent 的规划职责；服务负责保存候选关系、调度边、记录取证结果并验证已完成图的推导支持。

## 1. 先区分两件事

### 1.1 查询已知后继节点

对当前节点 `S` 调用 `get_vertex`：

```json
{
  "sessionId": "release-v1.2.0",
  "vertexId": "evidence.ci-build-log"
}
```

响应中的 `outgoingEdgeIds` 是图中已经存在、以 `S` 为来源的直接推理边。再对每个边 ID 调用 `get_inference_edge`，即可读取该边的目标节点和所属公式组。

`get_context_for_vertex` 适合读取当前节点的**上游**依赖和证据摘要，不是查询下游后继的工具。需要查看整个会话已有图时，使用 `get_reasoning_context` 的 `snapshot`。

### 1.2 发现未知后继节点

若 `S` 没有合适的出边，或已有出边不足以推进任务，Agent 需要根据 `S` 的语义、领域规则和已有图提出规划问题：

```text
已知 S 成立时，可以支持什么结论？
该结论是否还需要其他前提同时成立？
该结论是一个中间 State，还是现有的 Goal？
是否存在多条彼此独立的替代推导路径？
```

这一步不是 MCP 工具的返回值。Agent 产生候选结论和所需的同级前提后，再用顶点与推理边工具把它们写入图。

## 2. 单节点展开算法

设当前节点为 `S`。

1. 调用 `get_vertex(sessionId, S)`，读取已有 `outgoingEdgeIds`；必要时逐条读取边详情。
2. 调用 `get_context_for_vertex(sessionId, S)`，了解 `S` 已有的上游支持，避免把未经证实的状态当作可靠前提。
3. Agent 针对 `S` 生成一个或多个候选结论公式，例如 `S ∧ P2 -> T` 或 `S -> T`。
4. 为尚不存在的同级前提和目标创建顶点：直接材料使用 `Evidence`，中间结论使用 `State`；若目标已经是会话 Goal，则复用其 `goalVertexId`。
5. 对每个候选公式调用一次 `propose_inference_edge`，并保证当前节点 `S` 包含在 `sourceVertexIds` 中。
6. 将每个未到达 Goal、且仍可能产生下游结论的目标 `State` 作为新的当前节点，递归执行步骤 1-5。
7. 当达到 Goal、没有可接受的新结论、达到会话预算或遇到领域边界时停止展开；随后从已支持的来源向下完成候选边。

伪代码如下：

```text
expandForward(S):
  directSuccessors = get_vertex(S).outgoingEdgeIds
  upstreamContext = get_context_for_vertex(S)

  candidateFormulae = agentPlansConsequences(S, upstreamContext, directSuccessors)
  for each formula in candidateFormulae:
    siblingPremises = createMissingStateOrEvidenceVertices(formula.otherPremises)
    target = createOrReuseTarget(formula.target)
    propose_inference_edge(sources = [S, ...siblingPremises], target = target)

  for each target that is an unresolved State:
    expandForward(target)
```

## 3. 示例：从“CI 构建日志”正向展开

假设会话 Goal 为：

```text
G：版本 v1.2.0 可以发布
```

当前节点是已记录的直接证据：

```text
S：本次 CI 构建日志显示 pnpm build 成功
```

### 3.1 查询已有出边和上游支持

先调用 `get_vertex` 检查 `S` 是否已经参与过推理关系：

```json
{
  "sessionId": "release-v1.2.0",
  "vertexId": "evidence.ci-build-log"
}
```

如果 `outgoingEdgeIds` 为空，表示当前图中尚未记录从该构建日志出发的结论；它不表示构建日志不能支持任何结论。

再调用 `get_context_for_vertex`，确认该日志自身是否属于当前任务、是否存在冲突或重复的上游描述：

```json
{
  "sessionId": "release-v1.2.0",
  "vertexId": "evidence.ci-build-log"
}
```

### 3.2 Agent 提出后继结论公式

Agent 根据构建规则分析：仅有构建日志不足以可靠地推出“构建通过”，还需要产物校验记录。

```text
F1：CI 构建日志 ∧ 构建产物校验记录 -> 版本构建通过
```

这里：

```text
S  = CI 构建日志
P2 = 构建产物校验记录
T  = 版本构建通过
```

`P2` 是同级前提，`T` 是新产生的中间结论。不能因为正在从 `S` 正向展开，就错误地建立 `S -> T`；那会丢失 `P2` 这一必要条件。

### 3.3 创建缺失节点并提出公式

假设创建会话后先写入了 `S`，当前 `graphRevision` 为 `2`。先创建目标 `State`：

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 2,
  "vertexId": "state.build-passed",
  "label": "版本 v1.2.0 构建通过",
  "payload": { "version": "v1.2.0" }
}
```

再创建同级 `Evidence` 前提：

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 3,
  "vertexId": "evidence.build-artifact-check",
  "label": "构建产物校验记录有效",
  "payload": { "version": "v1.2.0", "verified": true }
}
```

最后将完整前提集合一次提交到目标：

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 4,
  "sourceVertexIds": [
    "evidence.ci-build-log",
    "evidence.build-artifact-check"
  ],
  "targetVertexIds": ["state.build-passed"],
  "label": "CI 构建日志和产物校验记录共同支持构建通过",
  "evidenceQuestions": [
    {
      "prompt": "CI 构建是否以退出码 0 完成，且产物校验记录对应同一版本？"
    }
  ]
}
```

服务创建两个物理边，并将它们放入同一 `formulaId`：

```text
CI 构建日志       -> 构建通过  (E1)
产物校验记录      -> 构建通过  (E2)

公式 F1：E1 ∧ E2，即 S ∧ P2 -> T
```

`evidenceQuestions` 会复制到该批次的每条物理边。若不同前提需要不同的问题，可在创建公式组后，对各条仍处于 `Candidate` 状态的边分别调用 `update_inference_edge` 设置完整问题列表。

### 3.4 继续向下游展开

现在把 `T` 作为当前节点：

```text
当前节点 T：版本 v1.2.0 构建通过

正向规划：T 可以支持什么结论？
P3：安全审计通过
G ：版本可以发布

F2：T ∧ P3 -> G
```

创建或复用 `P3`，并使用会话创建时返回的真实 `goalVertexId` 作为目标：

本例中，创建 `F1` 后图版本为 `5`；先以该版本创建 `state.security-reviewed`，再使用其响应中的版本 `6` 提交下面的公式。`P3` 本身仍需由安全审计报告等上游证据支持，不能作为孤立 `State` 节点直接视为已证明。

```json
{
  "sessionId": "release-v1.2.0",
  "agentId": "release-agent",
  "baseGraphRevision": 6,
  "sourceVertexIds": [
    "state.build-passed",
    "state.security-reviewed"
  ],
  "targetVertexIds": ["<goalVertexId>"],
  "label": "构建和安全审计均通过，因此版本可以发布"
}
```

完整的正向规划和边方向如下：

```text
CI 构建日志 + 产物校验 -> 构建通过 ─┐
                                      ├-> 版本可以发布
安全审计报告 -----------> 安全审计通过 ─┘
```

规划时从左向右询问“接下来能推出什么”；实际边也从左向右保存、完成和参与支持计算。

## 4. AND 与 OR 的正确建模

### AND：当前节点与其他前提必须共同成立

```text
S ∧ P2 -> T
```

一次调用中提交完整来源集合：

```json
{
  "sourceVertexIds": ["S", "P2"],
  "targetVertexIds": ["T"],
  "label": "S 和 P2 共同支持 T"
}
```

同一次调用中的来源共享一个公式组。该组中每条边都完成，并且所有来源均被支持后，`T` 才能被正向推导支持。

### OR：当前节点和另一条路径可分别支持目标

```text
S  -> T
P2 -> T
```

使用两次独立调用：

```json
{
  "sourceVertexIds": ["S"],
  "targetVertexIds": ["T"],
  "label": "S 支持 T"
}
```

```json
{
  "sourceVertexIds": ["P2"],
  "targetVertexIds": ["T"],
  "label": "P2 支持 T"
}
```

两次调用形成两个公式组；任一完整组均可支持 `T`。

> 不要因为从 `S` 开始展开，就把 `S ∧ P2 -> T` 简化为 `S -> T`。这会把本应为 AND 的关系错误建模为单前提推导。

## 5. 状态、证据和结论的边界

| 项目 | 正向展开中的角色 | 在图中的表达 |
| --- | --- | --- |
| 当前来源 | 已知事实、证据或已支持的中间结论 | `Evidence` 或 `State` 顶点 |
| 同级前提 | 当前来源之外，公式还需要满足的条件 | `Evidence` 或 `State` 顶点 |
| 后继结论 | 由完整公式推出的新状态或目标 | 新建 `State` 或复用 `Goal` 顶点 |
| 证据问题 | 验证候选边是否可以完成 | `propose_inference_edge` 的 `evidenceQuestions` |

当前实现没有独立的 `Hypothesis` 顶点类型。若新建的目标 `State` 尚待推导，应尽快为它建立入边公式；没有入边公式的 `State` 会被视为基础条件，不应被误作未验证的假设。

## 6. 从规划切换到执行

正向展开只建立候选图，不等于结论已经成立。执行时应优先处理来源已具备支持的底层边：

1. 使用 `list_candidate_edges` 查看候选前沿。
2. 使用 `claim_inference_edge` 领取一条边，并保存返回的 `leaseId` 和 `context.contextHash`。
3. 使用 `answer_evidence_question` 回答该边的全部证据问题。
4. 使用 `complete_inference_edge` 提交结论；无法成立时使用 `block_inference_edge`。
5. 持续从来源到目标完成边。所有来源已被支持且同一公式组全部完成后，内核的正向闭包计算会使目标得到支持。

完成单条边时，服务不会替 Agent 自动生成新的后继节点或新的公式；后续展开仍需由 Agent 决定。

## 7. 最小检查清单

- [ ] 已通过 `get_vertex` 检查当前节点的已有出边。
- [ ] 未把 `get_context_for_vertex` 误当作下游查询接口。
- [ ] 每个候选结论都包含完整的前提集合，而非只保留当前节点。
- [ ] AND 前提在同一次 `propose_inference_edge` 调用中提交。
- [ ] OR 替代路径使用独立的 `propose_inference_edge` 调用提交。
- [ ] 新建中间 `State` 后，已为其建立或规划入边公式。
- [ ] 每次写操作都使用上一写操作返回的最新 `graphRevision`。
- [ ] 已到达 Goal、没有可接受后继或达到明确边界时停止继续展开。
