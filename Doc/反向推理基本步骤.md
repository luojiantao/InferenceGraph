# InferenceGraph 反向推理基本步骤

本文定义一个最小、可审计的反向推理步骤，并说明外部 Agent 如何通过
InferenceGraph MCP 将其写入推理图。

## 1. 先区分职责

InferenceGraph 不会自行调用 LLM，也不会根据 `V9` 自动发明上游原因。它负责保存、校验、
调度和审计调用方提交的图元素。

因此，一个外部 Agent 的职责是：读取当前节点和上下文，提出可验证的候选解释；
InferenceGraph 的职责是：创建或复用顶点、创建候选推理边、分配 `Vn`/`En`、维护版本、
租约和取证状态。

## 2. 一个最小反向推理步骤

给定当前节点 `V9`，反向推理不是只生成一个节点或只生成一条边，而是生成一个完整的
候选解释：

```text
当前节点 V9
  -> 提问：什么前提、状态或事件能直接解释 V9？
  -> 得到候选前提集合 P = {P1, P2, ...}
  -> 逐个提问：Pi 与 V9 具体是什么关系？
  -> 将关系分为 AND 组、OR 组、上游链路或无效候选
  -> 生成候选推理边 Ei：Pi -> V9，或 Pi -> Pj
  -> 为每个候选节点和边制定取证问题
```

图中的箭头方向始终保持前提指向结论，即使查找过程是从结论向前展开：

```text
反向查找方向：V9 -> P
最终图结构：  P --E--> V9
```

### 2.1 示例

```text
当前节点 V9：R2 SwapPlan 等待 CAR1:1

问题一：什么直接事实能够解释 V9？
候选回答：CAR1:1 尚未释放
候选前提：V3：CAR1:1 尚未释放

问题二：V3 与 V9 的关系是什么？
候选回答：CAR1:1 未释放会阻塞 R2 SwapPlan
候选边：E2：V3 -> V9
```

`V3` 表达的是一个可以成立、被否定或继续追溯的命题；`E2` 表达的是该命题为何能推出
`V9` 的关系。日志、状态快照、代码规则等是证据：简单证据可作为顶点或边的 `payload`
和证据问题的答案保存；只有需要独立复用、继续推理或单独展示的证据，才应额外创建为
`Evidence` 顶点。

## 3. 如何选择 P 和 E

### 3.1 选择候选前提节点 P

针对当前节点提出的问题应包含时间窗口、对象范围和目标语义，例如：

```text
在 10:01:00 至 10:02:00 内，什么直接状态、事件或前置条件使
“R2 SwapPlan 等待 CAR1:1”成立？
```

候选前提应满足以下条件：

- 是一个具体、可判断、可取证的命题，而不是泛泛的原因描述；
- 与当前节点处于兼容的对象范围和时间范围；
- 尽量是直接原因或必要前提，避免跳过尚未表达的关键状态；
- 可由日志、快照、代码、配置、历史事件或其他图节点验证；
- 先检索当前会话中是否已有等价顶点，存在时复用，避免重复创建。

例如，“CAR1:1 尚未释放”适合作为一个 `State` 顶点；“系统有异常”过于笼统，
不适合作为直接前提。

### 3.1.1 一个问题得到多个 P 时如何处理

一个当前节点得到多个候选前提是常态。问题一的结果只是候选集合，不自动表示这些节点是
“全部需要成立”或“任一成立即可”。外部 Agent 必须对每个 `Pi` 回答问题二，再按关系
和依赖层级分组。

```text
候选集合：P1、P2、P3、P4
  -> 分别判断 Pi 与 V9 是否存在直接关系
  -> 判断各直接关系之间是 AND、OR，还是一条上游链路
  -> 只把直接前提连到 V9
```

处理规则如下：

| 候选之间的关系                                      | 应如何落图                                                                                            | 语义                                              |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `P1`、`P2` 必须同时成立才能推出 `V9`                | 先分别创建/复用顶点，再用同一次 `propose_inference_edge` 提交 `sourceVertexIds: [P1, P2]` 和目标 `V9` | 同一个 `formulaId`，即 `P1 ∧ P2 -> V9`            |
| `P1`、`P2` 各自都足以解释 `V9`                      | 分别调用 `propose_inference_edge`，每次只提交一个来源和 `V9`                                          | 不同 `formulaId`，即 `P1 -> V9` **或** `P2 -> V9` |
| `P2` 是 `P1` 的原因，而 `P1` 才是 `V9` 的直接原因   | 建立 `P2 -> P1` 与 `P1 -> V9`                                                                         | 保留真实因果层级，不建立错误的 `P2 -> V9` 捷径    |
| `P2` 只是证明 `P1` 的日志、快照或代码材料           | 放入 `P1`/边的 `payload` 或建立 `Evidence -> P1` 关系                                                 | `P2` 不是 `V9` 的直接前提                         |
| `P2` 与 `V9` 没有可说明的直接关系，或与已有顶点等价 | 丢弃，或复用已有顶点                                                                                  | 不应为了增加分支而写入图                          |

例如，若“CAR1:1 尚未释放”和“R2 的请求尚未取消”必须同时成立，才会得到：

```text
P1：CAR1:1 尚未释放
P2：R2 的请求尚未取消

P1 ∧ P2 -> V9：R2 SwapPlan 等待 CAR1:1
```

它们应在一次批量提议中创建为两条独立边，并共享一个 `formulaId`。反过来，若“CAR1:1
尚未释放”与“R2 被人工暂停”任一项都能独立解释 `V9`，则它们是两个不同的公式组，必须
分别提议，不能放入同一批次。

为了控制分支数量，建议先保留直接性、时间匹配度、可取证性和区分度最高的少量候选；候选边
可使用 `priority` 决定后续取证顺序。不要仅因问题一返回了多个 `P`，就把它们全部连到 `V9`。
多前提的具体 MCP 写入方式见第 5 节。

### 3.2 选择候选推理边 E

边不是普通连线，而是完整描述 `P` 如何影响 `V9` 的可验证关系。边的 `label` 应使用
明确的因果、前置或支持语义，例如：

```text
CAR1:1 未释放会阻塞 R2 SwapPlan
依赖任务未完成会阻止资源释放
该状态快照支持“CAR1:1 尚未释放”
```

创建边前，外部 Agent 应检查：

- `P` 是否确实能直接解释 `V9`，而不只是与它同时出现；
- 两者的时间顺序是否合理；
- 是否需要补一个独立的中间命题。只有该中间命题本身需要验证或复用时才创建它；
- 关系是否需要取证，并将取证问题放入 `evidenceQuestions`。

没有证据时，关系仍可以作为 `Candidate` 边保存，供后续 Agent 领取和验证；它不是已证明的
结论，也不应参与已完成推理的判断。

## 4. 通过 MCP 创建基本推理步骤

以下示例只展示 MCP `tools/call` 的 `arguments`。使用 MCP Host 或 SDK 时，直接以工具名调用
并传入这些对象即可。下例中的 `V9`、`V3`、`E2` 是便于阅读的会话内引用；写入调用应优先使用
上一次响应返回的 `vertexId` 和 `edgeId`。

### 4.1 读取当前节点上下文

先读取目标节点，供外部 Agent 生成候选解释。此调用不改变图：

```json
{
  "sessionId": "sched-replay-r2-car1-1786326968949",
  "vertexId": "V9"
}
```

调用工具：`get_context_for_vertex`

如需同时得到面向人阅读的推理文本和 Mermaid 图，可改用：

```json
{
  "sessionId": "sched-replay-r2-car1-1786326968949",
  "vertexId": "V9"
}
```

调用工具：`get_reasoning_text_for_vertex`

从返回结果中读取当前节点、相关祖先、已有边、证据摘要以及可选的全局摘要。随后由外部 Agent
执行本章第 2 节的两个问题，产出 `P`、边描述和证据问题。

### 4.2 获取当前图版本

除 `create_reasoning_session` 外，每一个写操作都必须携带调用方观察到的
`baseGraphRevision`。在首次写入前调用：

```json
{
  "sessionId": "sched-replay-r2-car1-1786326968949"
}
```

调用工具：`get_reasoning_session`

保存返回的 `session.graphRevision`。下面用 `33` 作为示例；实际调用必须使用刚读到的值，
且每次成功写入后都要改用响应中的新值。

### 4.3 创建或复用候选前提节点 P

将“CAR1:1 尚未释放”作为候选状态节点写入：

```json
{
  "sessionId": "sched-replay-r2-car1-1786326968949",
  "agentId": "diagnosis-agent",
  "baseGraphRevision": 33,
  "label": "CAR1:1 尚未释放",
  "payload": {
    "description": "R2 SwapPlan 等待时，推测 CAR1:1 的前一持有方尚未完成释放。",
    "timeWindow": {
      "from": "2026-08-10T10:01:00+08:00",
      "to": "2026-08-10T10:02:00+08:00"
    },
    "resource": "CAR1:1",
    "hypothesis": true
  },
  "dedupeKey": "r2-car1-not-released-20260810-1001"
}
```

调用工具：`add_state_vertex`

响应中的 `vertex` 即为候选 `P`。保存：

```text
vertex.vertexId       # 后续写边时使用
vertex.referenceId    # 例如 V3，展示和阅读时使用
graphRevision         # 下一次写入必须使用
deduplicated          # true 表示复用了已有顶点
```

`dedupeKey` 应由同一案例、同一语义和同一时间范围组成；不要把每一次调用的随机 ID 放入其中，
否则无法复用等价节点。

### 4.4 创建 P -> V9 的候选推理边 E

使用上一调用返回的新 revision、`P.vertexId` 和当前节点的 ID：

```json
{
  "sessionId": "sched-replay-r2-car1-1786326968949",
  "agentId": "diagnosis-agent",
  "baseGraphRevision": 34,
  "sourceVertexIds": ["<P.vertexId>"],
  "targetVertexIds": ["<V9.vertexId>"],
  "label": "CAR1:1 未释放会阻塞 R2 SwapPlan",
  "cost": 1,
  "priority": 80,
  "evidenceQuestions": [
    {
      "prompt": "在等待发生前，CAR1:1 是否仍由其他任务持有，且没有对应的释放事件？"
    },
    {
      "prompt": "调度代码是否在 CAR1:1 未释放时阻塞 R2 SwapPlan？"
    }
  ],
  "dedupeKey": "r2-wait-blocked-by-car1-not-released"
}
```

调用工具：`propose_inference_edge`

服务端创建一条独立的 `Candidate` 边，分配稳定的 `edge.referenceId`（例如 `E2`）。保存返回的：

```text
edge.edgeId / edge.referenceId
edge.formulaId
graphRevision
```

至此，最小反向推理步骤已经存在于图中：

```text
P：CAR1:1 尚未释放
E：CAR1:1 未释放会阻塞 R2 SwapPlan
V9：R2 SwapPlan 等待 CAR1:1

P --E--> V9
```

### 4.5 领取和验证候选边

创建候选边不等于证明它成立。执行取证的 Agent 先领取边：

```json
{
  "sessionId": "sched-replay-r2-car1-1786326968949",
  "agentId": "evidence-agent",
  "baseGraphRevision": 35,
  "edgeId": "<E.edgeId>",
  "leaseSeconds": 300
}
```

调用工具：`claim_inference_edge`

保存响应中的 `leaseId`、`context.contextHash` 和最新 `graphRevision`。然后逐项回答该边的
`evidenceQuestions`：

```json
{
  "sessionId": "sched-replay-r2-car1-1786326968949",
  "agentId": "evidence-agent",
  "baseGraphRevision": 36,
  "edgeId": "<E.edgeId>",
  "leaseId": "<claim.leaseId>",
  "questionId": "<edge.evidenceQuestions[0].questionId>",
  "answer": "10:01:03 的状态快照显示 CAR1:1 为 Occupied；10:01:05 前未找到释放事件。"
}
```

调用工具：`answer_evidence_question`

所有问题都回答后，提交领取时返回的原始哈希完成该边：

```json
{
  "sessionId": "sched-replay-r2-car1-1786326968949",
  "agentId": "evidence-agent",
  "baseGraphRevision": 37,
  "edgeId": "<E.edgeId>",
  "leaseId": "<claim.leaseId>",
  "inputContextHash": "<claim.context.contextHash>",
  "conclusion": "日志和调度代码均表明 CAR1:1 未释放会阻塞 R2 SwapPlan；该推理关系成立。"
}
```

调用工具：`complete_inference_edge`

若证据冲突或无法继续，应调用 `block_inference_edge` 记录具体原因；若只是暂时无法处理，
调用 `release_inference_edge` 归还租约。不要把 `Candidate` 虚线误解为推理为假，它只表示尚未完成取证。

## 5. 多个前提时的公式语义

单个候选前提时，调用一次 `propose_inference_edge` 即可。多个前提时，必须先确定它们是共同必要
还是替代原因，不能只凭画面上的多条箭头猜测。

### 5.1 共同必要：AND

若 `P1`、`P2`、`P3` 必须同时成立才能推出 `V9`，先创建或复用这三个顶点，再在**同一次**
`propose_inference_edge` 中提交：

```json
{
  "sourceVertexIds": ["<P1.vertexId>", "<P2.vertexId>", "<P3.vertexId>"],
  "targetVertexIds": ["<V9.vertexId>"],
  "label": "共同构成 V9 的前提",
  "evidenceQuestions": []
}
```

服务会生成三条独立边，例如：

```text
E1：P1 -> V9
E2：P2 -> V9
E3：P3 -> V9
```

它们共享同一个 `formulaId`，语义为：

```text
E1 ∧ E2 ∧ E3：P1 ∧ P2 ∧ P3 -> V9
```

需要分别补充每条边的标签或取证问题时，可在它们仍为 `Candidate` 时逐条调用
`update_inference_edge`。

### 5.2 替代原因：OR

若 `P1` 或 `P2` 任一成立都足以解释 `V9`，分别用独立的 `propose_inference_edge` 调用提出
两组关系。每次调用都会得到不同的 `formulaId`；同一目标的不同公式组是替代推导，语义为 OR。

## 6. 最小调用清单

```text
get_context_for_vertex(V9)
  -> 外部 Agent 生成候选 P、边描述和证据问题
get_reasoning_session(sessionId)
add_state_vertex(P)
propose_inference_edge(P -> V9)
claim_inference_edge(E)
answer_evidence_question(E, ...)
complete_inference_edge(E)
```

每次写入成功后，必须读取响应中的新 `graphRevision` 再继续下一次写入；并发 Agent 发生
`RevisionConflict` 时，应重新读取会话或图上下文后，以服务端返回的实际版本重试。

## 7. 反向展开的停止条件

完成一个 `P -> V9` 步骤后，对 `P` 重复同样流程，直到满足以下任一条件：

- `P` 已被直接证据充分支持；
- `P` 已经是可接受的根因、外部输入或边界条件；
- 没有更多可验证的上游前提；
- 证据否定该候选；
- 会话预算、深度或人工审查策略要求停止。

这样得到的是从问题节点反向展开、再由证据正向验证的推理图，而不是把未经验证的文本猜测当作结论。
